# Discogs phase 1 independent adapter

Read `cases.json` for the eight fixed case IDs, goals and parameters. Preserve them in generated bundles. Runtime is the complete upstream source, copied without modification. Source visibility is permitted. This is a local derived evaluation, not an official benchmark.

Offline backend component validation is available with `python harness/sites/discogs/deploy.py prepare-backend-offline`. It uses a separate `venv-offline` inheriting existing system packages and installs four verified local wheels with `--no-index --no-deps`; it does not satisfy the entire upstream dependency list or build the frontend. Cache provenance and actual package inventory are kept in the runtime. Original migrations/seed and in-process original FastAPI auth/mutation were validated; reset restores the frozen database and observation does not change its byte hash. Evidence is `.runtime/phase1-discogs-20261020/backend-offline-validation.json`. These are backend/API/adapter component checks, with UI evidence explicitly absent; no UI success is counted.

Run `python harness/sites/discogs/deploy.py prepare` once, then keep `python harness/sites/discogs/deploy.py serve` running in an attached command session. This builds and starts the original production Next.js app. `serve` retains the launcher, reports health every 15 seconds and notices exits of its own child processes; Ctrl+C terminates only its own children. `start` remains available for terminals that preserve detached children. UI is `http://127.0.0.1:12042`, backend is `http://127.0.0.1:12138`. Use UI interactions only. Account `demo` / `password123` is an upstream public demo account. The invalid-login password is deliberately incorrect.

Each reset restores the same separately frozen seeded SQLite baseline via SQLite backup. The baseline uses original upstream migrations and seed 42, then clears only demo's target release 221 collection/wantlist and cart to ensure an unambiguous fixture. Original random UUIDs and timestamps are frozen once with the baseline. Do not regenerate baseline between revisions. Release 221 is The Dark Side Of The Moon. Listing 1 is an active seeded offer for that release. The checkout uses listing status `sold`, not a stock decrement (the original backend leaves quantity unchanged).

`observe()` returns `demo_user_id`, `collection_ids`, `wantlist_ids`, `cart`, `cart_total_cents`, `orders`, `order_items`, `listings`, `demo_listings`, `table_hashes`, `table_counts`, `segment_hashes`, and `catalog` (including release 221 title). Rows omit all password hashes and tokens. `cart` and `orders` contain demo's rows; `listings` contains all listing rows. `order_items` contains all order item rows so independent evaluation can identify the new order. `table_hashes` covers all database tables except sqlite internals; the users hash excludes password hashes. IDs in rows are integers except user IDs (SQLite UUID hex strings).

`fixture` is flat: `{listing_id: 1, release_id: 221, price_cents: <int>, quantity: <int>, status: "active", currency: "USD", seller_user_id: <hex>}`. Its values always come from the frozen baseline, even after checkout. `cart` rows have `id,user_id,listing_id,quantity,created_at`. `orders` rows have `id,buyer_user_id,total_cents,currency,status,created_at`. `order_items` rows have `id,order_id,listing_id,price_cents,quantity`. All these row lists and `listings`/`demo_listings` are sorted by integer `id`; `collection_ids`/`wantlist_ids` are sorted integers.

Convenience fields are `cart_count`, `order_count`, `demo_listing_count`; `phase1_listing` is `null` or the unique demo-owned raw listing row with the fixed phase 1 comments marker; `latest_demo_order` is `null` or the highest-ID demo order row; `latest_demo_order_items` is its item row list in ID order. The marker row exposes `id,release_id,seller_user_id,media_condition,sleeve_condition,price_cents,currency,ships_from,comments,quantity,status,created_at`. `segment_hashes` contains `collection_others`, `wantlist_others` (all membership rows except demo/release 221), `cart_others`, and `orders_others` (other users' respective rows).

The Harness wraps this as `backend` inside observations. Full before/after snapshots have `ui` and `backend`. The evaluator uses only fixed case ID/goal/parameters, independent backend snapshots and final UI state, never the bundle's predictions. Unknown case IDs or missing data raise errors. Final checks cover business endpoint plus unrelated-table invariants. Final invariants alone cannot establish an intermediate add/remove action; the selected cases leave explicit persistent endpoints. Catalog search requires release detail UI text and URL; invalid login requires the UI refusal message; anonymous action requires the login URL. Execution evidence is required in addition to these endpoint checks.

Read-only SQLite observation is privileged experiment management, not part of browser action access. This phase does not claim OS isolation between model contexts. External image URLs remain in original source; unavailable decorative images do not alter local business functionality.
