## 2. 目前最有价值的表示组合

在已经尝试的有限方案中，值得继续发展的组合是：**短规则书＋共享的可执行状态模型＋参数化组件结构＋外部数据槽＋有歧义状态的实体注册表**。尚无证据称它最大化了 Agent 的理解。

v004/v005 的人读规则书只有 12 行、约 2 KB；证据没有堆进正文。复杂性主要放在共享程序、组件结构和独立检查里。简短规则书本身不保证这些层一致，双注册表反例正说明仍需检查它们的连接。

- **短规则书**记录功能、前置条件、原生 Playwright 定位方式、身份条件和必须停读的情况；运行证据另放侧索引。规则书不是唯一真值。
- **共享状态模型**在动作前返回预计业务变化、UI 合同和下一状态假说；真实动作及独立检查通过后，脚本才提交状态。离线说明和真实执行使用同一套函数。
- **参数化结构**约束稳定容器、重复项的内部结构、字段与按钮的归属、控件状态。它不要求预测整个 DOM／AX 的所有节点与外部文本。
- **外部数据槽**事前声明未知字段，动作后从真实观察绑定。未知值可以继续参与确定性计算；未知业务含义不能用空值掩盖。
- **实体注册**将业务对象与显示正文分开，保存当前可见身份条件、候选集合和因果线索。当前页面节点对应不等于跨页业务身份；可变点赞数也不是永久 ID。

v004 的搜索前合同只有同一个 `ready` 分支，可以容纳零项或多项。每项存在时都必须满足局部结构；零项时子项检查明确为“不适用”，不是凭空增加通过数。DOM 与 AX 通过实际捕获的节点对应关系核对集合，不按数组顺序配对。

这个机制仍有范围边界：如果两侧选择器同时遗漏同一个对象，两侧相等仍可能通过。检查器不会自动知道作者没有声明的组件。需要独立业务检查和新的覆盖反例继续约束。

## 3. 用一次搜索说明完整流程

以下是已实现接口的说明，不是另一次网站测量，也不新增网站规则。

1. 脚本调用共享模型，输入已确认状态和搜索参数。模型在动作前给出：表单值、结果容器、0..N 行的共同结构、DOM／AX 对应关系，以及本动作不应产生的持久业务写入。行数和行内文字保持未知。
2. Harness 保存这份预测，脚本通过原生 Playwright 执行操作。在这一动作的检查点，后续操作暂停。
3. Harness 独立采集 DOM／AX。若得到多行，逐行检查字段和控件是否存在、是否属于同一行，并检查两棵树是否覆盖同一批已选对象。若为零行，验证容器和空集合关系，子项计数为零。
4. 实际标题、公司等字段进入观察绑定通道，再经共享归一化函数进入状态。它们不获得“提前猜对内容”的分数。独立后台检查同时确认业务效果及禁止副作用。
5. 如果公开任务条件足以唯一确定目标，脚本可以计算下一步并连续执行。若当前查询没有目标，只有这次查询的未命中被确认，不能推断整个任务无法完成；是否继续查询取决于任务和已知规则。
6. 若结构矛盾、身份不唯一或新内容需要语义判断，保留原因并停止后缀。一次正确停读不等于任务完成。

## 4. 已确认的消费者结果

固定三个任务的输入在消费者生成前登记；每版全部脚本先冻结，再执行和反馈。消费者初次生成使用独立 Solar 上下文，后续是同一上下文适应。各版任务没有被删掉或改成更容易的任务。

| 版本 | 固定分母 | 完整通过 | 已执行但未完整通过 | 未执行 |
| --- | ---: | ---: | --- | ---: |
| v001／初次生成 | 3 | 0 | 1 项业务终点达到但正常退出未确认；2 项停读 | 0 |
| v002／适应 | 3 | 0 | 无真实浏览器执行，发现模型守卫错误后停止 | 3 |
| v003／适应 | 3 | 1 | 2 项停读，业务终点未达到 | 0 |

| v005／适应 | 3 | 0 | 无真实浏览器执行，状态接口组合仍可产生冲突 | 3 |

v001 第一项执行了 11 个动作，初态、动作和终态检查均通过，独立业务目标也达到；但 worker 退出码为 143，正常完成未确认。两类外层清理收据均记录剩余进程为零，不能误读为已经证实进程泄漏。一个可能原因是原先固定 12 秒的完成等待不足以容纳结束归档；本轮没有完成同字节换引擎重放来隔离确认这一原因。后续新引擎给完成清理有界的更长等待，并保持总预算约束，不追溯修改旧结果。

v003 第一项实际执行 11 个动作，内部 controller 记录约 96.71 秒，业务目标、动作门禁和清理全部通过；这是统一模型支持真实消费者执行的有效证据。其余两项各执行 7 个动作后停读：一项遇到同正文对象写入的能力边界，一项在首次返回集合中未找到目标。后者不能称为“任务不可达”或“后端没有这个对象”。

这个已通过流程的具体内容是：填写账号及错误密码 → 提交并收到拒绝 → 纠正密码并重新登录 → 打开编辑器、填写新正文、提交 → 跳转到另一页面 → 返回 → 刷新并确认刚创建的对象仍存在。独立后台最终确认仅新增一个对象，没有新增评论、反应或无请求的职位写入。11 个原生操作及对应屏障摘要见[脱敏完整流程：发布汇总摘录](../RESULTS.json)（原始 SAFE-FLOW-EXAMPLE.json 未归档）。

字段级检查存在强相关性，例如同一个任务会反复检查认证与业务计数。它们不作为独立任务扩充分母。controller 返回耗时也不是模型学习、脚本生成和所有准备在内的完整成本。

v004 的消费者 helper 对每次填写都调用 `input_value()`，对密码框也如此；原先冻结的浏览器边界允许填写密码，但禁止读取秘密控件值。第二次填写完成后即触发 `BoundaryError`，未进入业务流程。这是消费者接口误用，不是后台业务规则或双注册表反例。共同 helper 的另两个任务保留为未执行，修订另列为 v005，未放宽边界。

v006 固定三项已全部运行：第一项 11 动作、约 89.00 秒，完整通过；第二项 7 动作后停在同正文写入边界；第三项 11 动作后停在详情归属确认。三次均退出码 0、浏览器和 oracle 清理确认。第三项确实执行了第二次查询并选中公开唯一目标，但尚未保存、申请或验证跨页持久性。

第三项的公开观察归因是：公司与地点属于同一个复合 metadata 元素，消费者却分别使用孤立的 `get_by_text(..., exact=True)` 确认，因而找不到。已另登记单项诊断修订 007（本地历史引用，未随精选包归档；来源：`TARGETED-CONSUMER-007.json`）：分母为原第三任务这 1 项，模型、主脚本、checkpoint 与查询策略不变，只允许修正 helper 的文本粒度确认并保留完整身份条件。它不替换 v006 的三项结果。

**007 最终未运行，0 浏览器、0 动作。** 协调器准备的交接清单同时把可修改 helper 列为必须保持旧哈希的输入，导致一次前置断言冲突；这属于本轮交接缺陷，不是消费者违规或模型业务错误。随后新 wrapper 因剩余时间不足预先登记的 200 秒运行加 60 秒收尾而拒绝入场。没有临时缩减预算或修改旧注册。修复后的 helper 已冻结、静态检查通过，但没有真实运行成绩；不得把 v006 改写成 2/3。

已另存恢复闭包（本地历史引用，未随精选包归档；来源：`consumer-targeted-007 / RECOVERY-CLOSURE.json`）：22 个不可变输入均保持哈希，唯一变化是已授权修改的 helper，最终输出另行冻结。后续验收必须新登记运行、重置环境，并分别核对输入来源与允许修改的输出，不能直接重启已过期的旧 wrapper。

作者前一构造运行共 6 次浏览器调用、50 个动作；v004 新构造运行另有 2 次调用、19 个动作。其中一个真实探针用同一事前结构得到零项和多项；另一个创建同正文对象，验证可见候选歧义并按计划停读。作者对自己的采集做匹配和负控，不等于独立消费者通过。

## 6. 尚未解决的问题

1. **实体身份到动作的贯通。** v004 能保存同正文的两个候选，但部分动作仍以正文作为键，无法消费更丰富的身份。因此“能表达”还没有完全转化为“能可靠操作”。
2. **查询策略与任务规划。** 当前结果未命中应推动有根据的下一次查询或明确停读，而不是误判全局不可达。模型支持什么、消费者是否使用，必须分别检查。
3. **定位稳定性。** 公开身份及组件结构比位置更有意义，但部分父选择器仍依赖 class，当前集合唯一也不保证跨页永久唯一。本轮尚未系统扰动后端返回顺序、数据、布局与并发更新。
4. **覆盖与评分。** 容器、逐项、两树对应和后台业务事实各解决不同问题。尚未对所有可访问组件、所有分支遍历验证，也没有全站组件完整性证明。
5. **独立性与因果结论。** 浏览器 worker 有强制命名空间边界，模型 shell 仍只是指令隔离；严格成绩保持 null。仅一个站点、固定少量任务、一次重复，没有同知识同预算的模型消融，不能声称增进理解的因果效应。

公开产物审查还发现 v004 的两个注册表可能互相矛盾：先在实体表登记一个状态，再以另一状态绑定正文表，原实现会接受；后续动作可能用旧值覆盖实体表。这是纯模型反例，尚未称为真实网站失败。定点修复 005（本地历史引用，未随精选包归档；来源：`TARGETED-ADAPTATION-005.json`）允许 300 秒、零浏览器学习，保留 v004 冻结包和真实结果。

v005 修复了这条原反例，但独立复查进一步发现“登记实体 → 绑定正文不存在 → 创建”可返回不满足自身一致性检查的状态。它不是已经证明在网站可达的业务失败，却暴露出模型接口不能保证内部状态闭合。于是登记定点修复 006（本地历史引用，未随精选包归档；来源：`TARGETED-ADAPTATION-006.json`），把成功输出的一致性也纳入守卫与组合回归。v005 的三任务因此保留为静态模型阻断、未执行；其消费者代码迁移时不改变策略。

这也修正了对“最合适数据结构”的判断：多加一个实体表并不足够。更值得验证的是**唯一的对象事实表，加可派生的显示字段索引**，而不是两份可以分别被改写的业务事实。当前兼容修复仍保留两表及一致性守卫；上述单一事实来源是下一步设计建议，不是本轮已经交付并比较过的实现。

v006 已完成有限回归：作者枚举有限操作序列、状态种子，记录 4,807 个检查；独立审查另执行 13 个调用步骤和 12 项短控制，已知反例被拒绝，正常链保持一致，拒绝不突变输入。它们分别记录，不相加冒充独立样本，也不是对无限状态空间的证明。参见[表示审查](REPRESENTATION-GUIDE.md)第 13 节。

继续推进有价值。最直接的下一步是先真实验收已冻结的 007 详情确认修复，再补上“实体身份被实际动作使用”，然后做少量冻结的新组合与后端扰动。查询未命中后的再次查询与唯一选中已经真实发生，后面的保存、申请和跨页持久性仍待这条消费者流程验证。现阶段扩很多网站或宣布第三阶段完成，都缺少证据。等窄业务范围内的正反控及独立任务稳定后，再设同知识、同预算、同反馈的模型消融，才有条件回答预测程序本身是否帮助了理解。
