# 扩容后的服务存活检查

本补充记录在 21/180 例已经封存、下一批尚未派发时发现的资源事件。新增实例 h 的监督器已证实因宿主可用内存低于 3 GiB 停止自有服务；注册前的 TCP 检查同时发现 a/b/c 已停止，其原因由独立审查依据原日志另记。此时没有在途正式模型案例，原有结果不改写。

先保留 a..f 六个运行实例，暂停无正式任务的 g..l 自有服务，为六个模型进程及浏览器留出内存。历史准入证明保留；服务恢复须另记启动标记、PID、真实健康检查、冻结代码哈希和数据库恢复前后证据，不把旧 readiness 文件当成实时存活证明。

新通用入口 `harness/phase2/run_parallel_v002.py` 复用 v001 队列及每例执行流程，在领取下一案例前检查全部登记 worker 的前端和后端 TCP 端口。服务失联时停止新领取，已经在途的案例自然结束。TCP 存活不能替代独立 UI、业务或隔离准入。

v001 调度器、案例 runner、目标业务函数、冻结模型、权限、每例预算和 180/540 分母不改；v002 入口另列实际调用路径及哈希。Windows 4 GiB、WSL 2 GiB 的派发门槛与站点原有 3 GiB 自有进程保护继续生效。此时六路持续容量仍需实际运行观察，不能据部署数量声称十二路持续容量已通过。

模型服务重试、超时和资源恢复另列管理证据，不重新执行已封存案例以消除首试失败，不把该批次用于严格速度对照。
